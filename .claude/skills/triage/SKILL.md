# triage

Read `.agents/tracker.md` for the label strings, commands and notify mechanism. Without it, ask Ruaridh to run `setup-project`.

Triage is for issues you did not create. Tickets `to-tickets` produced are agent-ready already; they only pass through here as a **wave** for the gate.

## Input 1: a proposed wave

1. **Take the wave file** from `to-tickets` (`.scratch/tickets/<date>-<slug>.wave.json`). It follows `references/input.md`: every ticket's exact body, its spec section, source quotes and rulings; closes and comments in `other_actions`; gates, rollout and no-ticket items in `panels`. Publisher fields (labels, edges, idempotency keys) ride along unrendered. Make sure every proposed action is in it and each ticket's context is present, or its absence is visible.
2. **Render**: `python3 <this dir>/scripts/render_triage.py <wave.json> <wave.html>`. Compare every sheet against the wave data and the spec: rank order, source quotes, nesting, closing panels. The page is self-contained (fonts embedded, no network).
3. **Gate**: open the page in Plannotator in the background following `references/serving.md`, with a fresh decision-file path; give Ruaridh the link; wait. A timeout or dismissal leaves the wave unpublished.
4. **Apply the decision.** Map each `Feedback on: <quoted span>` to its ticket, spec section or source (ask when a span is ambiguous). Apply rulings to the wave data and the spec together, keep source quotes verbatim, record interpretations in `rulings`. Re-render material changes with a fresh decision path and gate again.
5. **Hand back** the approved wave file and the decision record to `to-tickets`, which publishes exactly that data. This skill writes no tickets for a wave.

## Input 2: inbound issues

**Roles.** One category, `bug` or `enhancement`, and one state: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`. Unlabelled goes to `needs-triage`; from there to any other state; `needs-info` returns to `needs-triage` when the reporter answers. Conflicting states: flag and ask first.

Every comment you post starts with `> *Generated by an AI agent during triage.*`

**"What needs my attention"**: three buckets, oldest first: unlabelled; `needs-triage`; `needs-info` with reporter activity since the last triage notes. Counts and one line each; let him pick.

**Triage one issue:**

1. **Gather**: the whole issue (body, comments, labels, author, dates) and any earlier triage notes, so resolved questions are not re-asked. Check the codebase for an existing implementation by domain concept, and `.out-of-scope/` for a prior rejection (`references/out-of-scope.md`).
2. **Recommend** a category and state with reasons and a short summary of the relevant code. Wait for his direction.
3. **Verify the claim** before anything else: reproduce the bug from the reporter's steps, or run what a PR claims. Report confirmed (with the code path), failed, or insufficient detail.
4. **Shape it** if needed with `grill`, one round at a time.
5. **Apply the outcome:**
   - `ready-for-agent`: comment an agent brief (`references/agent-brief.md`). Its acceptance criteria become the ticket's Done-when.
   - `ready-for-human`: the same brief plus why it cannot be delegated; then notify the owner per `tracker.md` (kata: `kata notify <ref>`).
   - `needs-info`: triage notes (what is established, what is still needed, specific questions). When the reporter is Ruaridh, ask him through the Inbox instead of waiting on a comment.
   - `wontfix`: only with his yes. Already implemented: point to where it lives. Rejected bug: a polite explanation. Rejected enhancement: write or extend `.out-of-scope/<concept>.md` and link it.

A direct "move #42 to ready-for-agent" is trusted: confirm what you will change, then do it, and offer to write the brief if there is none.
