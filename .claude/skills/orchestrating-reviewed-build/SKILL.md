# Orchestrating a reviewed build

Start with an approved spec (`writing-build-spec`; `adversarial-spec-review` if requested). The coordinator integrates; builders work on isolated branches; QA tests in isolation; the human owns production gates. Use the project's issue, branch and deployment rules. For a five-phase document-to-spreadsheet build, read [the worked example](EXAMPLE.md) when mapping workstreams to PRs.

1. **Map and integrate.** Assign one workstream, worktree and branch per builder; several builders may feed one PR. Put shared contracts before parallel policies and a risky integration switch last, preserving the spec's exact PR grouping and order. Each phase PR bases on the previous one; record its builders, commits and checks. Integrate onto the stack while keeping default-branch merges for the authorized window. Remove only worktrees/branches you created, after proving their commits landed and no one still uses them. This step ends when every workstream has a phase, dependency, owner and passing phase checks.
2. **Review each phase against the spec.** Default to a DeepSeek builder for each ticket and an independent `openai-codex/gpt-6-sol` reviewer for the integrated phase (confirm model names with `pi --list-models`). Give the reviewer the spec, phase base/head, changed work, tests and ticket refs. The reviewer sends evidence-backed findings to the coordinator, not directly to a builder. Triage each finding against the spec; return actionable fixes to the owning builder, record justified rejections, and re-run checks/review on the revised phase. This step ends for each phase when its reviewed head and every finding's disposition are recorded; keep human PR review separate. Use `herdr-agent-handoff` for delegation where available.
3. **Prove in isolation.** A separate QA owner runs hand-built precision fixtures derived from the current prompts and code against targeted agents in a test environment; record Run IDs and outcomes on owning issues. Prove a production-store writer's pure projection and I/O validation with code tests instead of a Run against the real store. If isolation is unavailable, mark that QA track unproved. Separately harvest real cases into a machine-readable acceptance file keyed by stable identity, with workstream, source decision and expected values. Unknown outcomes have `expected: null` and a decision owner. Give the file to the evals owner. This step ends with QA evidence for each targeted behavior or a named gap, and every harvested case labelled proved or expectation-pending.
4. **Hold human review and deployment gates.** Present phase PRs in order for human review. Reconcile in-app or out-of-band edits before promotion. Production pushes, queue drains, contract promotion and data resets follow the project's human authorization procedure. If required, deploy from the reviewed top of the stack before merging; merge to the default branch only when authorized, in the specified order and time. Compare deployed content *and wiring* with reviewed source to establish what is running. This step ends with recorded approval, deploy evidence and the still-open human actions; an unreviewed stack remains pending.
5. **Accept the production outcome.** After the authorized production run, compare actual values with known expectations and report missing, partial or reverted outputs. Keep unknown expectations visible to their owner. Mark a ticket done only when its promoted behavior and applicable known proof cases pass. Hand off PR links/order, QA Run IDs, acceptance-file path, comparison results, running-content evidence and unresolved decisions. This step ends when every issue's status matches its evidence, not merely its merge state.
