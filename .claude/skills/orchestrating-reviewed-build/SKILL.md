# Orchestrating a reviewed build

Use after `writing-build-spec` and, when requested, `adversarial-spec-review`. The coordinator owns integration; builders own isolated workstreams; QA owns an isolated test environment; a human owns production-write gates. Apply the project's branch, issue and deployment rules rather than assuming a particular platform.

1. **Plan the stack from dependencies.** Assign each builder one workstream, worktree and branch; several builders may feed the same phase PR. Put shared contracts and renames before parallel policy changes; put a risky integration switch last so a missed deadline leaves a working intermediate state. Group related work into reviewable PR phases, each based on the preceding phase. If the spec fixes the number or grouping of PRs, preserve it exactly rather than compressing phases; if it does not, choose a small number. State which builder's commits land in which phase and the checks each phase must pass. An integration switch is last; describe the actual fallback path in the spec rather than inventing a feature flag, deadline breakdown or default state. The coordinator integrates onto the stack; it does not silently merge to the default branch. Remove only child worktrees/branches created for this build, after confirming their commits landed and no one still uses them.
2. **Run two independent proof tracks.** QA uses a separate test team/environment and hand-built precision fixtures derived from the current prompts, policy and code. Run targeted agents by hand; record Run IDs and outcomes on the owning issues. Keep production data stores off limits during rehearsal. For a component whose job is to write to the production store, prove its pure projection and I/O validation in code tests instead of pointing a test Run at the real store. If safe isolation is unavailable, stop that QA track and report the gap; don't re-label a production run as a test.
3. **Harvest real proof cases without running them in QA.** Maintain a machine-readable acceptance file keyed by stable case identity, with workstream, source decision and expected values. If an expected value is unknown, record the identifier, `expected: null` and the owner who will decide; it is a harvest, not a passing test. Give the file to the evals/golden-dataset owner. After the authorized production run, a post-run checker compares the promoted build's actual outputs against known expected values and reports missing, partial or reverted outputs; unknowns remain visibly unresolved. Put QA Run IDs and post-run evidence on their respective issues.
4. **Hold the human gates.** Present the stacked PRs in dependency order for review. Confirm any prerequisite in-app or out-of-band edits before promotion. A production push, queue drain, simultaneous contract promotion or data reset happens only under the project's explicit human authorization and procedure. Deploy from the reviewed top of stack if the project requires a pre-merge production run; merge to the default branch only when authorized, in the specified order and at the specified time. Prove what is running by comparing deployed content and wiring with the reviewed source; revision labels or a successful push are not proof.
5. **Close on outcomes.** Record the state of each issue truthfully: written, integrated, reviewed, promoted, and accepted are different stages. Close a ticket as done only when its promoted behavior and applicable known proof cases pass; for an unknown expected result, name the outstanding owner rather than claiming acceptance. Hand off the PR links/order, QA Run IDs, acceptance file, deploy evidence, unresolved cases and human actions remaining.

**Worked example (fictional):** A five-PR stack has (1) shared schema and matcher, (2) parallel policy rewrites, (3) pure row projection plus spreadsheet I/O checks, (4) approvals, verifier and docs, and (5) a risky publisher switch. An isolated QA agent runs synthetic document cases against the latest policy but never opens the production spreadsheet; the publisher gets code tests. A real row with an unsettled expected cell goes into the acceptance file with `expected: null`. The human reviews all five PRs, authorizes the production window and deploy from the top branch; the default branch merges only on later authorization. The row's ticket becomes done only after its promoted output passes post-run comparison.
